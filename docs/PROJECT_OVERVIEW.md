# معرفی و دامنه پروژه FMMS

این سند مرجع مشترک برای شناخت مسئله کسب‌وکار، نقش‌ها، دامنه‌ها و گردش کار سامانه است. جزئیات فنی در [TECHNICAL_ARCHITECTURE.md](TECHNICAL_ARCHITECTURE.md) و ارتباط SAP در [SAP_INTEGRATION_GUIDE.md](SAP_INTEGRATION_GUIDE.md) آمده است.

## ۱. هدف سامانه

FMMS سامانه مدیریت نگهداری و تعمیرات ناوگان است. سامانه چرخه عملیاتی زیر را مدیریت می‌کند:

```text
اطلاعات پایه خودرو و راننده از SAP
  -> بازرسی روزانه و ثبت کیلومتر
  -> گزارش خرابی
  -> تصمیم واحد توزیع
  -> تصمیم واحد ترابری
  -> تعمیرگاه داخلی یا بیرونی
  -> درخواست و مصرف قطعه / تدارکات
  -> تحویل خودرو و بستن جریان تعمیر
  -> ثبت اسناد متناظر در SAP
```

SAP مرجع اصلی Master Data و اسناد رسمی سازمانی است. PostgreSQL دیتابیس عملیاتی FMMS برای workflowها، وضعیت‌ها، سوابق و audit است.

## ۲. وضعیت واقعی و معماری هدف

برای جلوگیری از تکرار تناقض‌های اسناد قدیمی، هر قابلیت باید یکی از وضعیت‌های زیر را داشته باشد:

| وضعیت | معنی |
|---|---|
| پیاده‌شده | در کد فعلی Django وجود دارد و با تست یا مسیر اجرایی قابل مشاهده است |
| ناقص/نیازمند سخت‌سازی | پیاده شده، اما برای Production ایراد یا تصمیم باز دارد |
| هدف آینده | در نیازمندی کسب‌وکار آمده، ولی جزئی از واقعیت فعلی کد نیست |
| تاریخی | مربوط به prototype یا معماری قبلی است و نباید مبنای توسعه جدید باشد |

قابلیت‌های اصلی Vehicle، Driver، Inspection، Fault، Repair، Material، Handover، Preventive Maintenance، Procurement، Integration و Authentication در Backend فعلی وجود دارند. گزارش‌گیری تحلیلی پیشرفته، storage سازمانی فایل، ورود یکپارچه SAP/SSO و بعضی BAPIهای تعریف‌شده هنوز نیازمند تکمیل یا تصمیم معماری‌اند.

## ۳. نقش‌های عملیاتی

| نقش | مسئولیت اصلی |
|---|---|
| Driver | مشاهده خودروی تخصیص‌یافته، بازرسی، ثبت کیلومتر، گزارش خرابی و تأیید تحویل |
| Distribution Supervisor | بررسی اولیه خرابی و تصمیم درباره قابل استفاده بودن خودرو |
| Transport Supervisor | تأیید و ارجاع تعمیر، کنترل تعمیر بیرونی و تأیید نهایی ترابری |
| Workshop Supervisor | تصمیم فنی تعمیرگاه مرکزی و مدیریت جریان تعمیر داخلی |
| Technician | فعالیت تعمیر، قطعات و عملیات فنی مجاز |
| Warehouse | بررسی موجودی و گردش قطعه |
| Supervisor | دسترسی نظارتی گسترده‌تر بر workflowهای عملیاتی |
| Admin | مدیریت کاربران، تنظیمات و عملیات مدیریتی حساس |
| Viewer | مشاهده read-only در محدوده مجاز |

مجوز نقش به‌تنهایی برای عملیات مالک‌محور کافی نیست. برای Driver باید تعلق خودرو/assignment/handover نیز کنترل شود؛ این موضوع در backlog امنیتی باز است.

## ۴. مالکیت داده

### SAP مالک است

- اطلاعات پایه خودرو و تخصیص راننده
- کاتالوگ اجزای قابل بازرسی
- کاتالوگ خرابی
- Material و موجودی انبار مرکزی
- اسناد رسمی مانند PM Notification، PM Order و Purchase Requisition

### FMMS مالک است

- Inspection و نتیجه آیتم‌ها
- Fault و تصمیم‌های workflow
- Repair Order، فعالیت‌ها، قطعات و timeline
- تحویل خودرو
- درخواست داخلی قطعه و snapshot تصمیم موجودی
- وضعیت workflow تدارکات
- تاریخچه integration و retry
- اطلاعات امنیتی و نقش‌های داخلی FMMS

### اصل همگام‌سازی

داده SAP-owned در FMMS cache یا snapshot محلی است و از داخل FMMS نباید به‌عنوان Master Data ویرایش شود. داده عملیاتی FMMS در PostgreSQL نگهداری می‌شود و در نقاط لازم سند رسمی SAP تولید می‌کند.

| Fault | ثبت خرابی، شدت، تصمیم توزیع و ارتباط اعلان SAP |
| Repair | سفارش تعمیر، تعمیرگاه داخلی/بیرونی، فعالیت، قطعه، هزینه و timeline |

## ۶. جریان‌های اصلی

### ۶.۱ خواندن اطلاعات پایه از SAP

```text
Celery یا API مدیریتی
  -> RunSAPSyncService
  -> OData Adapter
  -> SAP OData یا Mock
  -> Mapper
  -> Repository
  -> PostgreSQL
```

گروه‌های فعال فعلی شامل خودرو/راننده، قالب بازرسی، کاتالوگ خرابی و موجودی مرکزی است.

### ۶.۲ بازرسی و خرابی

1. راننده/کاربر مجاز Inspection را ایجاد می‌کند.
2. آیتم‌های چک‌لیست ثبت و Inspection submit می‌شود.
3. آیتم‌های ناموفق می‌توانند به یک Fault تجمیع شوند.
4. Fault وارد تصمیم Distribution می‌شود.
5. در صورت غیرقابل استفاده بودن خودرو، Repair Order ساخته یا ادامه داده می‌شود.

### ۶.۳ تعمیر داخلی

1. Transport تعمیر را تأیید و نوع تعمیرگاه را تعیین می‌کند.
2. Workshop تصمیم فنی می‌گیرد.
3. فعالیت، قطعه و هزینه داخلی ثبت می‌شوند.
4. تکمیل فنی، Handover ایجاد می‌کند.
5. Driver تحویل را قبول یا رد می‌کند.

### ۶.۴ تعمیر بیرونی

1. درخواست ارجاع بیرونی ایجاد و تأیید می‌شود.
2. assignment تعمیرگاه بیرونی ثبت می‌شود.
3. تحویل و دریافت خودرو ثبت می‌شوند.
4. review، خدمات، قطعات و فاکتور ثبت می‌شوند.
5. Transport جریان را می‌بندد.

### ۶.۵ تأمین قطعه

1. Material Request از Repair Order ایجاد می‌شود.
2. موجودی مرکزی بررسی و تصمیم stock/purchase ثبت می‌شود.
3. در صورت خرید، Purchase Requisition ایجاد می‌شود.
4. PR از مسیر SAPTransactionManager به SAP ارسال می‌شود.

## ۷. محدوده آینده

- ورود سازمانی از طریق SAP Identity/SSO یا IdP سازمان
- گزارش‌گیری و KPIهای ناوگان
- object storage خصوصی برای پیوست‌ها
- تکمیل wiring واقعی BAPI/RFC
- outbox یا الگوی قابل اتکاتر برای هماهنگی DB و SAP
- تست‌های concurrency و PostgreSQL-specific
- مانیتورینگ end-to-end و runbook عملیاتی
